## Permanent code fixes landed tonight (still on disk, not committed)

- **`neuroai/features/llm.py`** — added a guard (search for
  `_NullTritonDriver`) that pre-empts a `RuntimeError: 0 active drivers`
  crash from Triton when `import fla` gets triggered on a CPU-only node
  (happens via `transformers.dynamic_module_utils.check_imports` eagerly
  validating a trust_remote_code model's declared imports — e.g. Lanni-ni
  stickbreaking/alibi/forgetting/hard-n-gram families — regardless of
  whether that specific model actually uses fla at runtime). Verified fix
  with a direct reproduction before landing it. Only activates when
  `torch.cuda.is_available()` is False; a real GPU still gets Triton's real
  driver.

- **`scripts/run_lpp_lme_sweep.py`** — fixed `require_cached_surprisal`
  handling. `configs/lpp_lme_sweep.yaml` has this key present with an
  explicit `null`, and `dict.get(key, default)` only applies `default` when
  the key is **absent**, not when it's explicitly `None` — so the intended
  "require a cache hit on CPU, don't silently reload the model" safety
  behavior was silently defeated on every `--device cpu` run. This caused
  **every** family with a cache miss to attempt a live model load + forward
  pass on 4 CPU cores, including a doomed attempt to load OPT-66B (~264GB in
  fp32) that would never have finished. Fixed to treat explicit `null` the
  same as "key absent".

- **`scripts/slurm/jz/embedding/geco/{bloom,rwkv4}.sh`**,
  **`scripts/slurm/jz/embedding/{meco,ucl_reading}/{bloom,rwkv4}.sh`** —
  switched `gres=gpu:2` → `gpu:1`. Neither family's largest checkpoint
  actually needs 2 GPUs (bloom max 7.1B ≈14GB, rwkv4 max 14B ≈28GB, both
  fit easily on one 80GB H100); the 2nd GPU was actively harmful because
  `contextual_word_embeddings_hf_fulltext`'s multi-GPU branch respawns a
  fresh model-loading subprocess **per document call** when >1 GPU is
  visible, and GECO's ~415 short (single-chunk) documents made this
  catastrophically slow for no benefit (only 1 of 2 GPUs ever got work).

- **`neuroai/benchmarks/n400_szewczyk.py`** — replaced the per-(subject,
  layer) `ThreadPoolExecutor` (3,450+ tiny GIL-contended tasks) with a
  per-subject `ProcessPoolExecutor` (mirroring `geco_embed.py`'s proven
  pattern), for the CPU regression path. Root cause: many small
  sklearn/NumPy calls under threads don't release the GIL long enough for
  real parallelism; real multiprocessing was needed. Also added a
  `--regression_device` CLI flag (`scripts/run_szewczyk_checkpoint_sweep.py`)
  decoupling the ridge-fit device from the LLM-forward-pass device, so
  feature extraction stays on GPU (fast) while the fit runs on CPU
  (sidesteps a separate, undocumented cuSOLVER concurrency hang that GPU
  concurrent `torch.linalg.svd` calls hit for large hidden dims). Validated:
  bloom-1.7B went from "never completes" to 14 minutes.

- **`scripts/slurm/jz/job_szewczyk_jz_common.sh`** — capped BLAS thread env
  vars (`OMP_NUM_THREADS` etc.) at a fixed 2 instead of tying them to
  `cpus-per-task`, since the real parallelism now comes from
  `N_GPU_WORKERS`, not per-fit BLAS threading.
